# Standard x402

[x402](https://www.x402.org) is the open standard for charging per HTTP request: the server answers `402 Payment Required` with the payment requirements, the client signs the payment and repeats the request. On Stellar it is implemented by the official `@x402/stellar` packages: the client signs only the **authorization** of the USDC transfer and a **facilitator** assembles the transaction, submits it and pays the network fee, so the payer needs no XLM.

Kiba speaks x402 in both directions, with the official packages.

## Pay any x402 API from the assistant

The `call_url` tool in the connector (and `POST /v1/x402/call` in the API) lets the assistant pay an API that charges with x402 on Stellar even if it is not in Kiba's catalog.

```text
User:      Call https://api.example.com/weather?city=Bogota and tell me the weather.
Assistant: call_url({ url: "https://api.example.com/weather?city=Bogota" })
```

What Kiba does:

1. Calls the URL without payment. If the API does not answer 402, it returns the response as is, without charging.
2. Reads the payment requirements from the `PAYMENT-REQUIRED` header and picks the Stellar option in USDC.
3. Deducts the price from the user's balance (credits, or the payments wallet when there are no credits).
4. Signs the transfer authorization with Kiba's treasury and repeats the request with `PAYMENT-SIGNATURE`.
5. The API verifies and settles on-chain through its facilitator and answers with `PAYMENT-RESPONSE`, which carries the transaction hash.

The answer to the assistant includes the API result, `cost`, `newBalance`, `payTo`, `txHash` and `explorerUrl` (stellar.expert). The call is saved in the account's results and the charge in the transactions, with the transaction signature.

Rules:

- **Per-call cap.** 1 USD by default. If the API charges more, Kiba does not pay and tells the assistant to retry with `maxUsd`. There is a hard cap of 20 USD.
- **Refund.** If the API rejects the paid call without settling, the charge goes back to the balance. If it settled and still answered an error, the payment is already on-chain and the response says so.
- **Public destinations only.** `https` URLs without credentials and outside private networks.
- **Methods** GET, POST, PUT, PATCH and DELETE, with a JSON body and custom headers. Payment headers are set by Kiba.

`call_url` parameters: `url` (required), `method`, `body`, `headers`, `maxUsd`.

## Charge with x402 on your service

Every service published with the SDK can accept, besides Kiba's quote, standard x402 payments from **any** client. One environment variable or one config field turns it on:

```bash
npm i @x402/core @x402/stellar      # Node 22 or newer
KIBA_X402_FACILITATOR=https://x402.org/facilitator   # or `self`
```

```ts
new AgentProvider({
  service: 'my-service',
  pricePerCall: 0.01,
  x402: { facilitatorUrl: 'https://x402.org/facilitator' }, // or { selfFacilitate: true }
});
```

With x402 on:

- The 402 carries the `PAYMENT-REQUIRED` header with the price of **that** request (the dynamic price from `priceFn` included), your account as `payTo` and USDC on your network. The body is still Kiba's quote, so the connector works as before.
- A request with `PAYMENT-SIGNATURE` is verified before anything runs: network, asset, account and amount must be those of your service for that request. If it is valid, your handler runs and then the payment is settled on-chain. The 200 carries `PAYMENT-RESPONSE` with the hash and `_payment.standard = "x402"`.
- If the payment is invalid or does not settle, the answer is 402 with the reason and a fresh quote, and the result is not delivered.
- The manifest advertises `x402: { network, payTo }` so clients know they can pay you this way.

Facilitators:

| Option | What it does | When |
|---|---|---|
| `https://x402.org/facilitator` | Verifies, submits the transaction and pays the fee. No key. | Testnet |
| OpenZeppelin Channels | Same, with an API key (`KIBA_X402_FACILITATOR_API_KEY`). | Testnet and mainnet |
| `self` | Your own service verifies and submits the transaction with its account and pays the fee (about 0.00001 XLM) from its XLM. No third party. | Testnet and mainnet |

Your account needs a USDC trustline to receive payments; `bootstrap()` creates it.

## How it fits with Kiba's rail

| | Kiba's rail | x402 lane |
|---|---|---|
| Who pays whom | The assistant pays catalog services | The assistant pays any x402 API; any x402 client pays your services |
| Charge | Credits or payments wallet, signed by the platform, in milliseconds | One USDC transaction per request, settled by a facilitator |
| Settlement to the service | Kiba's payments contract, in batches, with the 95/5 split | Straight to your account, 100% of the price |
| Licenses | The payment carries the license document's fingerprint | Not applicable |

x402 is the interoperability lane: it opens the catalog outwards and brings clients in from outside. Kiba's rail remains the fast path inside the assistant.

## Examples

- [`examples/x402-seller`](https://github.com/CoKeFish/kiba/tree/main/examples/x402-seller): a third-party API that charges with x402 (`@x402/express`) and that Kiba pays with `call_url`.
- [`examples/x402-buyer`](https://github.com/CoKeFish/kiba/tree/main/examples/x402-buyer): a generic x402 client (`@x402/fetch`) paying a Kiba service without the connector.

```bash
curl -X POST https://api.kiba.tools/v1/x402/call \
  -H "Authorization: Bearer $KIBA_TOKEN" -H "Content-Type: application/json" \
  -d '{ "url": "https://api.example.com/weather?city=Bogota", "maxUsd": 0.05 }'
```
